# 【数学小讲师联盟】·执行流程 V0

> 项目目标：一周内重建并上线可运行的【数学小讲师联盟】网站 MVP  
> 项目角色：Hermes / 助手作为“流程控制器”；犟爸作为执行方与最终确认人  
> 核心机制：阶段锁 + 交付物验收 + 变更控制 + 每日推进  
> 文档版本：V0

---

## 0. 总体判断

犟爸提出的执行流程整体是**合理的，而且非常适合当前项目状态**。

原因是：当前【数学小讲师联盟】不是一个从零开始的纯技术项目，而是一个已经有旧网站、已有页面、已有风格尝试、但产品定位刚刚重新校准的重建项目。此时最大的风险不是“代码写不出来”，而是：

1. 首页风格未定，反复修改；
2. 首页修改影响分页；
3. 分页临时发明样式；
4. 产品内容越加越多；
5. 视觉先行导致结构失控；
6. 一周目标被不断扩展，最终 MVP 无法上线。

因此，使用“阶段锁”是必要的。

> 这个项目一周内能否成功，不取决于我们能不能想到更多功能，而取决于我们能不能坚决冻结阶段、控制范围、按交付物推进。

---

## 1. 该流程是否能支持一周内完成 MVP？

结论：**可以支持，但需要做三点增强。**

犟爸原流程已经覆盖了：

- 内容清单；
- 信息架构；
- 低保真线框；
- 视觉规范；
- 高保真设计；
- 前端开发；
- 测试上线；
- 阶段锁；
- 变更控制；
- 每周报告。

这些是正确的。

但如果目标是一周内完成可运行 MVP，还需要补充三项控制：

### 1.1 增强一：明确“一周 MVP”的范围边界

一周内不应追求完整产品，而应追求：

> 可访问、可理解、可点击、主流程清楚、页面一致、能支撑早期 30 人小讲师试运行。

也就是说，MVP 的重点不是所有后台和真实复杂逻辑全部完成，而是先完成一个可运行的产品骨架。

### 1.2 增强二：每个阶段必须有时间盒

如果没有时间盒，阶段锁可能变成“无限打磨”。

因此每个阶段都需要限定时间。例如：

- 阶段1：0.5-1 天；
- 阶段2：1 天；
- 阶段3：1 天；
- 阶段4：2.5-3 天；
- 阶段5：1 天。

### 1.3 增强三：设置 MVP 降级策略

如果某个功能来不及做完整，必须有降级方案。

例如：

- 真实视频上传来不及，可以先做上传入口和状态占位；
- 自动标签来不及，可以先做人工标签；
- PBL 复杂组队来不及，可以先做项目介绍 + 报名入口 + 任务书页面；
- 积分自动结算来不及，可以先做展示规则和积分流水结构占位；
- 老师后台统计来不及，可以先做审核入口和待审核列表占位。

这样才能保证一周内上线 MVP，而不是卡在某个复杂功能上。

## 2. 项目角色与权责

### 2.1 Hermes / 助手：流程控制器

职责：

1. 控制阶段推进；
2. 拒绝跳阶段；
3. 检查交付物是否符合验收标准；
4. 标记交付物状态；
5. 触发变更控制；
6. 每次对话汇报当前阶段；
7. 每周五生成进度报告；
8. 在范围失控时强制收敛；
9. 确保最终目标是一周内上线 MVP。

### 2.2 犟爸：执行方与最终确认人

职责：

1. 提供判断；
2. 确认交付物；
3. 执行或授权修改；
4. 不绕过阶段锁；
5. 对关键取舍做最终确认。

### 2.3 核心关系

在这个项目中，犟爸授予流程控制器“推进权”。

这意味着：

- 如果当前阶段未完成，即使犟爸要求跳到后面，流程控制器也应拒绝；
- 如果犟爸提出新增需求，流程控制器必须判断是否影响当前阶段；
- 如果影响已确认交付物，必须触发变更控制；
- 如果影响一周 MVP，必须提出降级或延期建议。

## 3. 一周 MVP 定义

### 3.1 MVP 必须做到

一周 MVP 应至少做到：

1. 网站可正常访问；
2. 首页能准确表达产品定位；
3. 主要分页存在且结构清楚；
4. 导航、footer、按钮、卡片风格统一；
5. 问答广场有清楚的页面结构；
6. PBL 项目营有清楚的页面结构；
7. 个人中心或成长页有基础结构；
8. 老师审核或后台入口有基础结构；
9. 手机、平板、电脑三端不明显崩坏；
10. 内容、链接、按钮、入口经过基础测试。

### 3.2 MVP 可以暂时不做到

一周内可以暂不完整实现：

1. 完整自动匹配算法；
2. 完整自动积分结算；
3. 完整视频处理链路；
4. 完整老师数据分析后台；
5. 完整 PBL 智能组队；
6. 完整消息通知系统；
7. 小程序；
8. AI 自动标签或 AI 审核；
9. 大规模运营数据图表。

这些可以作为 V1 或 V2。

### 3.3 MVP 的真正目标

MVP 的目标不是“功能全”，而是：

> 让目标家长和孩子看完网站后，能清楚理解这个产品是什么、适合谁、怎么参与、为什么不焦虑，并能进入问答广场或 PBL 项目营的基础流程。

## 4. 核心机制：阶段锁

项目分为 5 个阶段。

每个阶段包含：

- 交付物清单；
- 验收标准；
- 强制锁；
- 状态标记。

阶段未完成时，禁止进入下一阶段。

### 4.1 阶段锁规则

1. 阶段交付物未全部完成，不进入下一阶段；
2. 交付物必须由犟爸确认后，才能打勾；
3. 打勾后的交付物如需修改，必须触发变更控制；
4. 变更影响当前阶段时，当前阶段重新验收；
5. 变更影响后续阶段时，必须更新影响说明；
6. 不允许为了赶进度跳过阶段，只允许在阶段内做 MVP 降级。

---

## 5. 每次对话的固定开场格式

每次对话开始，流程控制器必须先汇报：

```text
当前阶段：阶段X｜阶段名称

已完成交付物：
✅ ...
✅ ...

待完成交付物：
□ ...
□ ...

当前正在处理：...

是否允许进入下一阶段：否 / 是
原因：...
```

如果当前阶段未完成，默认不讨论下一阶段具体执行。

## 6. 阶段1：内容清单

### 6.1 阶段目标

用纯文字确定每个页面必须呈现什么，删除旧网站干扰，避免后续设计和开发阶段反复加内容。

### 6.2 交付物

- □ 首页内容清单；
- □ 分页内容清单；
- □ 删除项说明。

### 6.3 首页内容清单要求

首页必须明确：

1. 产品名称与核心主张；
2. 一句话定位；
3. 适合谁；
4. 核心方式：孩子教孩子；
5. 两个核心板块：问答广场 + PBL 项目营；
6. 反焦虑承诺；
7. 家长与老师的边界。

首页总信息项不超过 7 个。

### 6.4 分页内容清单要求

每个分页单独列出，不允许把分页当成首页缩小版。

建议 V0 页面包括：

1. 首页；
2. 问答广场；
3. 问题详情页；
4. 上传问题页；
5. 上传讲题页；
6. PBL 项目营介绍页；
7. PBL 任务书页；
8. 个人中心 / 成长护照；
9. 家长进度页；
10. 老师审核页；
11. 登录 / 注册页。

如一周 MVP 时间不足，可把部分页面降级为占位页或合并页，但必须在内容清单中明确说明。

### 6.5 删除项说明要求

删除项说明必须回答：

- 旧网站哪些内容不保留；
- 为什么删除；
- 删除后是否需要迁移到其他页面；
- 是否影响 MVP。

### 6.6 验收标准

- 每个信息项能用一句话说清“用户看到它能理解什么”；
- 没有两个信息项表达同一意思；
- 每页总信息项不超过 7 个，超出必须说明为什么必须保留；
- 每个页面有明确任务；
- 每个页面知道自己“不负责什么”。

### 6.7 强制锁

以上 3 个交付物全部打勾，才能进入阶段2。

---

## 7. 阶段2：信息架构与线框

### 7.1 阶段目标

在不讨论颜色、字体、风格的情况下，确定页面层级、信息顺序、首屏重点和用户动线。

### 7.2 交付物

- □ 网站地图；
- □ 首页低保真线框；
- □ 各分页低保真线框；
- □ 用户动线说明。

### 7.3 网站地图要求

网站地图必须说明：

- 哪些是公开页面；
- 哪些是登录后页面；
- 哪些是孩子端页面；
- 哪些是家长端页面；
- 哪些是老师端页面；
- 哪些页面 V0 必做，哪些页面可占位。

### 7.4 低保真线框要求

线框只允许出现：

- 灰框；
- 黑白文字；
- 模块名称；
- CTA 名称；
- 页面跳转标注。

线框禁止出现：

- 颜色；
- 字体选择；
- 圆角；
- 阴影；
- 插画；
- 图标风格；
- 手绘效果；
- 渐变；
- 装饰性背景。

### 7.5 用户动线要求

至少覆盖：

1. 新家长第一次访问；
2. 孩子提问；
3. 小讲师认领讲题；
4. 提问孩子反馈“明白了 / 还有疑问 / 还是不懂”；
5. 孩子参加 PBL；
6. 老师审核；
7. 家长查看进度。

### 7.6 验收标准

- 线框中不允许出现任何颜色、字体、圆角、阴影；
- 每个页面有明确“第一眼区域”和“第二眼区域”；
- 任意两个页面的导航结构一致；
- 用户能从首页走到核心流程；
- 页面之间不存在重复入口或死路；
- 每个页面的主 CTA 不超过 2 个。

### 7.7 强制锁

以上 4 个交付物全部打勾，才能进入阶段3。

---

## 8. 阶段3：视觉规范系统

### 8.1 阶段目标

先建立全局视觉规范，再设计首页。首页是规范的第一个使用者，不是规范的定义者。

### 8.2 交付物

- □ 色彩规范文档；
- □ 字体规范文档；
- □ 间距规范文档；
- □ 组件库；
- □ 首页高保真设计稿。

### 8.3 色彩规范要求

必须包含：

- 主色 1 个；
- 辅助色 2 个；
- 文字色 3 个：标题 / 正文 / 次要；
- 背景色；
- 状态色：成功 / 警告 / 错误，可作为补充，不参与主要视觉风格。

建议方向：

- 主色：温暖橙，用于主要行动；
- 辅助色1：方格纸蓝，用于任务和信息；
- 辅助色2：成长绿，用于完成、采纳、徽章；
- 背景：象牙白 / 纸张色。

### 8.4 字体规范要求

必须定义：

- 页面大标题；
- 模块标题；
- 正文；
- 辅助说明；
- 按钮文字；
- 最小字号。

原则：低龄友好，但不幼稚；家长可信，但不冰冷。

### 8.5 间距规范要求

基础间距：

- 8px；
- 16px；
- 24px；
- 48px。

所有模块间距必须使用这些倍数，不允许临时发明。

### 8.6 组件库要求

V0 至少包括：

- 按钮 3 种状态：默认 / 悬停 / 禁用；
- 卡片 2 种样式：普通卡片 / 任务卡片；
- 输入框；
- 标签；
- 徽章；
- 页面标题；
- 问题卡；
- 项目卡；
- 老师审核状态；
- 空状态。

### 8.7 首页高保真要求

首页设计稿必须 100% 使用规范中的：

- 颜色；
- 字体；
- 间距；
- 组件。

禁止首页临时发明新样式。

### 8.8 验收标准

- 规范文档可直接交给另一个设计师，对方不问问题也能设计分页；
- 首页设计稿必须全部使用规范；
- 若首页需要新组件，必须先补充到组件库，再使用；
- 视觉风格必须符合“学习营 / 方格纸 / 任务卡 / 小讲师舞台 / 成长护照”的产品隐喻；
- 避免幼儿园化、糖果色、强游戏化。

### 8.9 强制锁

以上 5 个交付物全部打勾，才能进入阶段4。

---

## 9. 阶段4：分页高保真与开发

### 9.1 阶段目标

在已确认的内容、线框和视觉规范基础上，完成核心页面设计与前端实现。

### 9.2 交付物

- □ 各分页高保真设计稿；
- □ 开发环境搭建确认；
- □ 首页前端实现；
- □ 各分页前端实现；
- □ 跨页面一致性检查。

### 9.3 分页高保真要求

分页只设计“首页没有的新内容”。

继承首页和视觉规范中的：

- 导航；
- footer；
- 按钮；
- 卡片；
- 标签；
- 空状态；
- 页面标题样式。

分页不得临时发明样式。

### 9.4 开发要求

建议工程结构：

```text
components/ui/          基础组件
components/product/     产品语义组件
app/...                 页面组合
styles / globals.css    全局 token 与基础样式
```

页面应尽量组合组件，不在页面中写大量临时样式。

### 9.5 修改日志机制

任何页面修改都必须记录：

- 修改页面；
- 修改内容；
- 是否影响组件；
- 是否影响其他页面；
- 是否需要回到视觉规范更新。

### 9.6 验收标准

- 分页中出现的新组件必须先回到视觉规范中新增；
- 禁止在分页上临时发明样式；
- 任何页面修改需同步检查是否影响其他页面；
- 导航、footer、按钮、卡片、标签、间距一致；
- 页面实现与对应内容清单一致；
- 页面实现不得新增未经确认的信息项。

### 9.7 强制锁

以上 5 个交付物全部打勾，才能进入阶段5。

---

## 10. 阶段5：测试与上线

### 10.1 阶段目标

确保 MVP 可访问、可点击、内容准确、视觉一致、三端基本可用。

### 10.2 交付物

- □ 功能测试清单；
- □ 视觉一致性检查；
- □ 内容最终校对；
- □ 上线部署。

### 10.3 功能测试清单要求

必须覆盖：

- 每个导航链接；
- 每个按钮；
- 每个表单；
- 每个主要 CTA；
- 登录 / 注册入口；
- 问答广场入口；
- PBL 入口；
- 个人中心入口；
- 老师入口；
- 手机端关键入口。

### 10.4 视觉一致性检查要求

必须检查：

- 手机；
- 平板；
- 电脑。

检查内容：

- 导航是否可用；
- 文字是否过小；
- 卡片是否拥挤；
- CTA 是否明确；
- 图片或装饰是否遮挡内容；
- 页面是否横向溢出；
- 视觉风格是否统一。

### 10.5 内容最终校对要求

必须检查：

- 产品名称；
- Slogan；
- 目标用户；
- 反焦虑表达；
- 非 AI 替代；
- 同伴真实性；
- PBL 描述；
- 积分与徽章描述；
- 是否有过度承诺；
- 是否有制造焦虑的表达。

### 10.6 验收标准

- 测试清单逐条通过；
- 发现问题回到对应阶段修复；
- 修复后重新验收对应阶段；
- 上线后能通过公网访问；
- 最终交付上线地址和测试结果。

## 11. 变更控制机制

### 11.1 触发条件

以下行为触发变更控制：

1. 修改已打勾交付物；
2. 新增页面；
3. 新增首页信息项；
4. 新增视觉风格；
5. 新增组件；
6. 修改核心流程；
7. 修改目标用户；
8. 修改 MVP 范围；
9. 要求跳过阶段。

### 11.2 变更处理格式

每次变更必须说明：

```text
变更内容：
影响阶段：
影响页面：
影响组件：
是否影响一周 MVP：
是否需要重新验收：
建议处理：接受 / 延后 / 拒绝 / 降级
```

### 11.3 变更原则

- 不影响 MVP 的优化，进入待办池；
- 影响当前阶段的，当前阶段重新验收；
- 影响后续阶段的，更新后续交付物；
- 影响一周上线目标的，必须给出降级方案；
- 与产品底线冲突的，直接拒绝。

## 12. MVP 降级策略

为了保证一周上线，必须允许功能降级，但不允许价值观降级。

### 12.1 可以降级的内容

| 原设想 | MVP 降级方案 |
|---|---|
| 自动标签 | 人工标签 / 预设标签 |
| 智能匹配小讲师 | 手动推荐 / 简单规则匹配 |
| 完整视频上传处理 | 上传入口 + 状态展示 / 链接提交 |
| 自动积分结算 | 积分规则展示 + 手动流水占位 |
| 完整 PBL 组队系统 | 老师手动组队 + 项目页展示 |
| 完整老师数据后台 | 审核列表 + 基础状态 |
| 复杂通知系统 | 页面提示 + 手动群通知 |

### 12.2 不可降级的内容

以下不能降级：

- 无排行榜；
- 他人积分不可见；
- 不做 AI 替代孩子思考；
- 不把孩子表达标准化包装；
- 首页必须清楚说明产品定位；
- 页面风格必须统一；
- 主要入口必须可点击；
- 网站必须能正常访问。

## 15. 流程控制器行为规则 V0

### 15.1 每次对话必须先报状态

必须汇报：

- 当前阶段；
- 已完成交付物；
- 待完成交付物；
- 当前处理项；
- 是否允许进入下一阶段。

### 15.2 提交交付物后必须验收

犟爸提交一个交付物后，流程控制器必须对照验收标准逐条检查。

通过：打勾。  
不通过：说明缺什么，不打勾。

### 15.3 禁止同时推进多个阶段

当前阶段未完成时，不推进下一阶段。

如果犟爸要求跳过，回复：

> 当前阶段未完成，请专注完成【具体交付物】。阶段锁未解除，不能进入下一阶段。

### 15.4 修改已确认内容必须触发变更控制

如果犟爸修改已打勾交付物，流程控制器必须说明：

- 影响范围；
- 是否要重新验收；
- 是否影响后续阶段；
- 是否影响一周 MVP。

### 15.5 控制范围，不鼓励发散

流程控制器必须拒绝：

- 当前阶段外的细节讨论；
- 不影响 MVP 的延展功能；
- 会制造焦虑的设计；
- 会替代孩子思考的 AI 功能；
- 临时发明样式；
- 未经验收直接开发。

## 16. 对犟爸原流程的优化总结

犟爸原流程的核心是正确的：

> 内容先行，线框定结构，视觉系统定风格，高保真和开发继承规范，最后测试上线。

我建议在原流程上新增四个补强：

1. **MVP 范围定义**：明确一周内做什么、不做什么；
2. **时间盒**：避免阶段锁变成无限打磨；
3. **降级策略**：保证上线，不被复杂功能卡死；
4. **变更控制模板**：防止已经确认的内容反复返工。

## 17. 最终执行原则

本项目后续执行只遵守一句话：

> **先锁内容，再锁结构，再锁规范，再做页面，再测试上线。阶段未锁，不许前进。**

如果一周内要成功运行 MVP，必须坚持：

- 不追求完整大而全；
- 不因首页好看牺牲分页一致性；
- 不让旧网站内容干扰新定位；
- 不让新想法破坏阶段节奏；
- 不让 AI 或技术替代孩子思考；
- 不让积分和展示制造焦虑；
- 不让任何页面临时发明样式。

这就是【数学小讲师联盟】一周重建 MVP 的执行流程 V0。
