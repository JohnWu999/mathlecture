# 数学小讲师联盟｜代码实施管控与回退预案 V0

> 目的：在正式代码实施前，先把“哪些内容必须先定稿、如何分批开发、如何保留可回退版本、如何避免功能丢失”说清楚。  
> 背景：犟爸上次做网站时，虽然做了版本管理，但出现过 V1 效果不好想回退 V0 时功能丢失的问题。本预案的核心不是“出问题后再 git 回退”，而是**提前设计可切换、可验收、可冻结的实施秩序**。

---

## 一、正式代码实施前还需要犟爸审核/确认的内容

以下内容不需要全部重新讨论，但建议在动代码前做一次“冻结确认”。冻结不是永远不能改，而是避免开发中途频繁推翻底层规则。

## 1. P0 范围冻结

请确认第一版可运行 MVP 是否只包含以下 P0：

- 首页
- 你问我答
- 提交问题
- 问题详情 / 小讲师认领 / 上传讲解
- 项目营
- 项目详情 / 报名意向
- 项目小组协作空间
- 成果广场
- 个人中心 / 成长护照
- 老师工作台
- 管理员后台的最小数据与权限能力

建议暂不进入 P0 的内容：

- 复杂 AI 自动生成项目的一键发布
- 完整支付自动化
- 复杂实时协作
- 复杂视频剪辑/封面自动合成
- App / 小程序
- 大规模推荐算法

## 2. 视觉方向冻结

已确认方向：

- 总方向：无限生长的数学森林
- 首页：高保真 V1 灵动生命力版
- 分享海报：三类分享海报 V1
- 硬规则：图案不得遮挡文字安全区

仍建议犟爸确认：

- 首页 V1 作为 P0 默认首页方向，不再并行开发多个首页版本。
- V0/V1 等旧视觉稿作为参考与回退样本保留，不直接混入生产页面。
- 后续如果再改视觉，优先做“视觉分支/开关”，不直接覆盖已稳定功能。

## 3. 数据规则冻结

请确认以下规则作为 P0 数据基础：

- 成果公开 = 已审核 + 已授权公开。
- 不公开排行榜、不公开积分、不展示 Top/超过多少人。
- 三类身份：提问者 / 小讲师 / 探索家。
- 身份星级与积分、能力标签分离。
- 能力徽章放在成长护照，不作为公开竞争展示。
- 老师和管理员权限分开。
- 管理员导出/下载数据必须有审计日志。

## 4. 运营边界冻结

请确认：

- 免费问答保留完整闭环，但有温和额度。
- 免费项目不默认承诺老师 1:1 个性化反馈。
- 付费项目重点是项目包/主题项目营，而不是提问或小讲师视频收费。
- 付费报名先保留家长联系与人工确认，不做匿名付款码优先。
- 退出/请假规则先按 MVP 手动记录 + 后台可查。

## 5. 部署与验收边界确认

建议确认：

- 开发环境、预览环境、生产环境分开。
- 犟爸每次只审核“预览环境”或“截图/录屏”，确认后再进生产。
- 每个批次必须有验收报告，不能靠聊天口头确认。

## 二、为什么单纯 git 回退会导致功能丢失

上次出现“回退 V0 后功能丢失”的根本原因，通常不是 git 本身失效，而是把不同性质的修改混在了一起：

1. **视觉改动和功能改动混在同一个提交里**
   - 想回退视觉 V1 时，连带把后端接口、数据库字段或权限逻辑也回退了。

2. **数据库结构变化没有迁移策略**
   - 代码回去了，但数据库字段已经变了，旧代码读不到新数据，或新功能数据丢失。

3. **没有稳定主线与预览分支**
   - 所有尝试都直接在主分支上做，导致“哪个版本是稳定的”说不清。

4. **没有功能开关**
   - V0/V1 不能共存，只能互相覆盖。

5. **没有批次验收点**
   - 做到一半才发现方向不对，此时已经牵连太多模块。

所以这次的原则是：

> **不要把“回退”设计成事后撤销代码，而要提前设计成“稳定版本 + 实验版本 + 可切换开关 + 数据不倒退”。**

## 三、推荐实施架构：三条线并行但不混淆

## 1. 稳定主线：`master` / `main`

用途：

- 只保存已经验收通过的版本。
- 可随时部署。
- 不直接做实验。

规则：

- 每个批次通过验收后，才合并进稳定主线。
- 合并前必须构建通过。
- 每次合并后打标签。

建议标签：

- `baseline-before-mvp`
- `mvp-batch-1-visual-tokens`
- `mvp-batch-2-schema`
- `mvp-batch-3-homepage`
- `mvp-batch-4-qna`
- `mvp-batch-5-projects`
- `mvp-batch-6-share-hall`
- `mvp-batch-7-profile`
- `mvp-batch-8-admin-teacher`
- `mvp-v0-preview-approved`

## 2. 功能分支：每个批次一个分支

建议分支：

- `feat/mvp-batch-1-foundation`
- `feat/mvp-batch-2-schema`
- `feat/mvp-batch-3-homepage`
- `feat/mvp-batch-4-qna`
- `feat/mvp-batch-5-projects`
- `feat/mvp-batch-6-share-hall`
- `feat/mvp-batch-7-profile`
- `feat/mvp-batch-8-admin-teacher`

规则：

- 一个分支只做一个批次。
- 一个提交只做一类事情。
- 视觉、数据、业务逻辑、权限不要混在同一个提交。

## 3. 实验分支：视觉或交互尝试专用

用途：

- 首页 V2 尝试
- 海报 V2 尝试
- 新组件风格尝试

建议分支：

- `experiment/homepage-v2`
- `experiment/poster-v2`
- `experiment/project-card-v2`

规则：

- 实验分支不直接合并到主线。
- 先截图/预览给犟爸看。
- 认可后，再把必要改动“摘出来”进入正式功能分支。

## 四、工作区隔离方案：使用 git worktree

为避免当前工作目录越做越乱，建议正式实施时使用 worktree：

```bash
git worktree add .worktrees/mvp-batch-1-foundation -b feat/mvp-batch-1-foundation
```

每个批次在独立目录开发，例如：

```text
/home/ubuntu/Workspace/math-young-lecturer                 # 稳定主目录，不乱改
/home/ubuntu/Workspace/math-young-lecturer/.worktrees/mvp-batch-1-foundation
/home/ubuntu/Workspace/math-young-lecturer/.worktrees/mvp-batch-2-schema
```

必要规则：

- `.worktrees/` 必须加入 `.gitignore`。
- 每个 worktree 开始前先跑 `npm run build`。
- 每个 worktree 完成后生成验收报告，再决定是否合并。

## 五、功能开关方案：避免 V1 覆盖 V0

对容易被犟爸反复比较的内容，不直接删除旧版本，而是保留可切换能力。

## 1. 首页版本开关

建议结构：

```text
components/home/homepage-v1.tsx
components/home/homepage-v2-experiment.tsx
app/page.tsx
```

`app/page.tsx` 只负责选择：

```tsx
const homepageVersion = process.env.NEXT_PUBLIC_HOMEPAGE_VERSION || "v1";
```

这样如果 V2 不满意，回到 V1 是改环境变量或小范围切换，不需要回退整站代码。

## 2. 海报版本开关

建议结构：

```text
components/share/templates/poster-v1.tsx
components/share/templates/poster-v2-experiment.tsx
```

分享资产生成时记录：

```text
templateVersion = "v1"
```

这样旧海报不会因为新模板改动而失真。

## 3. 项目卡/成果卡版本开关

同理，视觉组件保留版本号：

```text
ProjectCardV1
ProjectCardExperiment
OutcomeCardV1
```

生产默认只使用已验收版本。

## 六、数据库迁移与数据保护方案

数据库是最容易在“回退代码”时造成损失的部分。因此要遵守：

## 1. 只做向前兼容迁移

优先新增字段，不轻易删除字段：

- ✅ 增加 `reviewStatus`
- ✅ 增加 `shareScope`
- ✅ 增加 `IdentityProgress`
- ❌ 直接删除旧字段
- ❌ 改字段含义但不保留映射

## 2. 每次 schema 改动前先备份

开发/预览环境：

```bash
pg_dump "$DATABASE_URL" > backups/pre-schema-$(date +%Y%m%d-%H%M%S).sql
```

生产环境：

- 必须先人工确认。
- 必须先备份。
- 必须有回滚说明。

## 3. Prisma 迁移单独提交

不要把 schema 改动和页面视觉混在一起。

提交示例：

```bash
git commit -m "feat(schema): add review and share scope fields"
```

## 4. 回退原则

- 页面视觉可以快速切换。
- 功能代码可以回滚到上一个 tag。
- 数据库一般不做破坏性回退，只做兼容修复。

---

## 七、提交与验收规则

## 1. 每个批次最小提交结构

推荐每批至少拆成：

1. `chore:` 常量、token、基础组件
2. `feat(schema):` 数据模型
3. `feat(page):` 页面/组件
4. `feat(api):` 接口/权限
5. `docs:` 验收报告

## 2. 每个批次必须通过

```bash
npm run build
```

后续建议增加：

```bash
npm run typecheck
npm run lint
```

## 3. 每个批次必须输出验收报告

文件格式：

```text
docs/阶段4-批次N-验收报告-V0.md
```

报告必须包含：

- 本批次改了什么
- 哪些规则已落地
- 构建结果
- 截图/预览地址
- 已知问题
- 是否建议合并进稳定主线

## 八、回退策略：按问题类型处理

## 情况 A：只是视觉不好看

不要 git revert 整个批次。

处理方式：

1. 切回已验收视觉组件版本。
2. 保留新功能和数据库。
3. 新视觉作为 experiment 分支继续改。

## 情况 B：某个功能有 bug

处理方式：

1. 优先修复该功能。
2. 如果影响严重，关闭功能入口或隐藏按钮。
3. 不回退无关模块。

## 情况 C：数据库迁移出问题

处理方式：

1. 暂停合并和部署。
2. 使用备份恢复预览环境。
3. 修正迁移脚本。
4. 重新跑验证。

生产环境不得临时手动乱改数据。

## 情况 D：整个批次方向错误

处理方式：

1. 稳定主线不合并该分支。
2. 直接废弃该分支或保留为 experiment。
3. 从上一个稳定 tag 重新开新分支。

## 九、正式开工前建议犟爸确认的 8 个问题

请犟爸在开工前确认以下 8 项：

1. **P0 范围**：是否确认第一版 MVP 就按本预案的一组页面和后台能力推进？
2. **视觉基准**：是否确认首页 V1、三类分享海报 V1 作为 P0 默认视觉基准？
3. **低焦虑边界**：是否确认不公开排行榜、不公开积分、不写 Top/超过多少人？
4. **付费边界**：是否确认 P0 付费重点是项目包/主题项目营，不是提问或小讲师视频收费？
5. **后台边界**：是否确认老师与管理员权限严格分离，导出下载仅管理员？
6. **版本策略**：是否确认采用“稳定主线 + 批次分支 + 实验分支 + tag”的方式？
7. **视觉回退策略**：是否确认视觉不满意时优先用组件版本开关切换，而不是整站 git 回退？
8. **验收节奏**：是否确认每个批次完成后先出验收报告和预览，再决定是否合并/部署？

## 十、我建议的最终开工门槛

满足以下条件再正式改代码：

- [ ] 犟爸确认本预案中的 8 个问题。
- [ ] 当前文档类成果先提交或打包归档，避免继续显示为未跟踪文件。
- [ ] `.worktrees/` 加入 `.gitignore`。
- [ ] 给当前稳定状态打 tag：`baseline-before-mvp`。
- [ ] 建立第一个 worktree：`feat/mvp-batch-1-foundation`。
- [ ] 在 worktree 中再次运行 `npm run build` 并通过。

## 十一、结论

这次不建议用“做乱了再回退”的方式管理网站，而建议采用：

> **先冻结规则，再分批实施；先保留稳定主线，再开实验分支；视觉用版本开关回退，数据库用向前兼容迁移保护；每批验收后再合并。**

这样即使犟爸觉得某一版视觉不满意，也可以只切回视觉版本，而不会把已经做好的问答、项目、成果广场、个人中心、后台权限等功能一起弄丢。
