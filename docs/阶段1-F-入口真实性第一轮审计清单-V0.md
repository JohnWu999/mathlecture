## 四、本轮发现的关键问题

### P0-1：线上示例项目 `projectType` 与 `price` 冲突

线上 `/api/projects` 返回：

```json
{
  "id": "proj_demo_001",
  "projectType": "PAID",
  "price": 0
}
```

判断：这会让家长误解“付费项目为何 0 元”，属于试运营前必须修正的数据/文案冲突。

建议：二选一，不能同时存在：

1. 如果是免费体验项目：改为 `projectType = FREE`，保留 `price = 0`；
2. 如果是付费项目：补真实价格，并在报名文案中明确“提交意向，管理员/企业微信跟进”。

本阶段建议先按免费体验项目处理，避免未正式收费前产生支付预期。

### P0-2：成果广场公开成果为空，存在“空壳感”

线上 `/api/hall` 返回：

```json
{"outcomes":[]}
```

虽然 API 规则正确，且空状态有授权规则说明，但作为第一批试运营入口，成果广场长期为空会让用户认为产品没有真实孩子作品。

建议：

- 若已有真实授权作品：导入 3 条已审核授权样例；
- 若暂无真实作品：前台空状态改成“第一批作品审核中”，并给出清晰下一步，不展示成像空系统。

### P0-3：老师工作台仍大量使用浏览器 `alert()` 作为核心反馈

`app/teacher/page.tsx` 中问题审核、讲解审核、成果审核、撤回、开放基础参与等动作仍使用 `alert()`。

判断：后端动作是真实的，但前端反馈方式不符合阶段1-F“真实状态反馈”的体验标准。用户点击后虽然有弹窗，但没有稳定留痕、没有页面内状态条，不利于运营人员连续处理。

建议：新增统一 `notice` 状态区，替代核心 `alert()`。

### P0.5-1：登录/注册成功仍使用 `alert()`

`app/login/page.tsx` 注册成功后仍使用：

```ts
alert("注册成功！请等待老师开放权限后登录");
```

建议改为页面内提示，不阻塞用户，也更符合儿童/家长端温暖体验。

### P0.5-2：线上公开问题存在历史数据状态不一致风险

线上 `/api/questions?status=OPEN` 中某条答案返回：

```json
{"status":"APPROVED","reviewStatus":"PENDING"}
```

规则测试要求讲解审核同步 `status` 与 `reviewStatus`，说明新代码路径已防回退；但线上历史数据仍可能有旧状态不一致。

建议：

- 增加一次线上数据修复脚本或后台兼容清理；
- 对 `Answer.status = APPROVED` 且 `reviewStatus != APPROVED` 的历史记录进行同步；
- 清理前先备份并记录影响行数。

## 五、建议下一批修复顺序

### 第一批：P0数据/空状态修复

1. 修正示例项目 `projectType/price` 冲突。
2. 成果广场空状态改成明确试运营说明，或导入 3 条授权样例。
3. 清理线上历史答案状态不一致数据。

### 第二批：P0.5前端反馈真实化

1. 老师工作台移除核心 `alert()`，改页面内 notice。
2. 登录/注册成功改页面内提示。
3. 老师/管理员连续处理动作后保留操作结果提示，并刷新对应列表。

### 第三批：端到端抽查

1. 学生上传题目照片并提交问题。
2. 老师审核问题。
3. 学生/小讲师认领并上传讲题视频。
4. 老师审核讲解。
5. 学生报名项目。
6. 管理员跟进报名并开通项目权益。
7. 学生提交项目作品。
8. 老师公开授权成果。
9. 成果广场可见后再撤回。

## 六、本轮结论

阶段1-F第一轮审计结论：

1. 当前线上不是纯假入口，核心 API、上传、权限保护、老师/管理员后台均已存在。
2. 阶段0遗留的重复 basePath 跳转未复现；`/teacher`、`/admin` 未登录均正确跳 `/math-young-lecturer/login`。
3. 真正需要优先处理的是“试运营可信度”：示例项目类型价格冲突、成果广场空壳感、历史答案状态不一致、老师工作台/登录注册仍用 alert。
4. 下一步应进入第一批 P0 修复，而不是继续生成说明文档。
