## 3. 最可能原因排序

### 原因 A：当前 Hermes 机器缺少这台生产服务器真正授权的私钥

证据：

1. 22 端口通；
2. SSH 服务正常；
3. 公钥已 offer；
4. 服务器拒绝；
5. 尝试多个用户名都拒绝。

这是当前最可能原因。

### 原因 B：生产服务器 `authorized_keys` 被改动或云主机重装/重置过

证据：

1. 之前项目历史中有过成功部署记录；
2. 当前同一批本地 key 不再被接受；
3. 如果近期服务器安全加固、重装、换镜像、重置密钥，就会出现此现象。

### 原因 C：实际可登录用户名不是 `ubuntu` / `root` / `lighthouse`

可能但优先级低。

如果服务器使用了自定义用户，例如 `deploy`、`www`、`app` 等，当前尝试会失败。需要从云控制台或历史部署记录确认。

### 原因 D：服务器 SSH 配置限制了特定来源或禁用了部分用户

可能但优先级低。

如果 `AllowUsers`、`DenyUsers`、`Match Address`、`PasswordAuthentication`、`PubkeyAuthentication` 等配置被改动，也可能导致此现象。由于当前无法登录，无法直接读取远端 `/etc/ssh/sshd_config`。

## 5. 推荐恢复方案

### 方案 1｜在云服务器控制台把当前 Hermes 公钥加入 `authorized_keys`（推荐）

需要把以下公钥添加到生产服务器可部署用户的 `~/.ssh/authorized_keys`：

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIOcLwzbof1CgkGJNNgRB2h/NreBYyVhlNJySuGoMn+Hy hermes-agent-for-jiangba
```

推荐添加到：

```text
ubuntu 用户
```

如果线上实际部署用户不是 `ubuntu`，则添加到真实部署用户。

添加后需要确保远端权限：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

然后我可重新测试：

```bash
ssh ubuntu@159.75.144.28 'hostname && whoami'
```

### 方案 2｜通过云控制台重置/绑定 SSH 密钥

如果不方便编辑 `authorized_keys`，可在云服务器控制台把当前 Hermes 公钥绑定到实例。

注意：不同云厂商“重置密钥”可能会覆盖原有密钥，请优先选择“追加/绑定”而不是覆盖；如必须覆盖，要先确认不会影响其他维护者登录。
